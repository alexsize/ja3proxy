# Техническое задание версии 3.0
## Регистратор TLS-отпечатков и центр управления JA3Proxy

> Версия: 3.0
> Статус: каноническая нормативная спецификация реализации
> Дата выпуска: 2026-09-23
> Базовый репозиторий: `alexsize/ja3proxy`
> Закреплённый TLS engine: `github.com/refraction-networking/utls v1.8.2`

## 1. Состав полного ТЗ

Версия 3.0 является единым нормативным комплектом из двух частей:

1. [Основное ТЗ версии 2](JA3Proxy_Fingerprint_Recorder_TZ_v2.md) — capture,
   fingerprints, хранение, routing, UI/API, безопасность, релизы и общие
   критерии приёмки.
2. [Нормативное приложение A: архитектура и профили uTLS](JA3Proxy_uTLS_TZ_Additions.md)
   — TLS generation engine, Profile Compiler, replay, fidelity, engine
   compatibility и дополнительные критерии проверки.

Обе части обязательны. Ссылка на «ТЗ v3» означает весь комплект, а не только
этот индекс. Версия 2 остаётся в репозитории как неизменяемая историческая
основа и самостоятельно больше не является канонической спецификацией.

## 2. Нормативные термины

Ключевые слова **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** и **MAY**
имеют смысл, установленный в разделе «Как читать документ» основного ТЗ.

В приложении A формулировки «добавить», «изменить», «уточнить», «нужно» и
«должен» означают **MUST**, если пункт явно не отнесён к рекомендации или
будущему релизу.

## 3. Разрешение конфликтов

При конфликте действует следующий приоритет:

1. безопасность, приватность и запреты MUST NOT BREAK;
2. actual network bytes и parsed actual network bytes;
3. приложение A для uTLS generation, replay и Profile Compiler;
4. критерии приёмки конкретного релиза;
5. основное ТЗ v2;
6. UI-примеры и рекомендуемые имена пакетов.

`ClientHelloSpec`, stored profile и preset name не могут отменить факт,
полученный из `RecordingConn`. Unknown extension не может быть молча отброшен.
При невозможности одновременно выполнить два MUST реализация прекращается с
явной ошибкой, а конфликт оформляется поправкой к ТЗ до продолжения работ.

## 4. Зафиксированная архитектура

```text
                         ANALYSIS
RAW CLIENTHELLO ──► наш parser ──► JA3 / JA4 / TLS-NORM / storage
       │
       └──────────────── GENERATION
                         uTLS Fingerprinter
                                │
                         ClientHelloSpec
                                │
                         Profile Compiler
                                │
                              uTLS
                                │
                         RecordingConn
                                │
                      ACTUAL OUTBOUND WIRE
                                │
                         JA3 / JA4 / Diff
```

Наш код отвечает за bounded capture/reassembly, parser, normalization,
analytics, persistence, profile management, audit и verification. uTLS
является единственным штатным execution/generation engine ClientHello. Свой
TLS serializer допускается только для функции, которую невозможно корректно
представить через закреплённую версию uTLS, после отдельного изменения ТЗ и
набора wire-level regression tests.

## 5. Источники истины

Нормативный порядок:

```text
1. Actual network bytes
2. Parsed actual network bytes
3. Compiled ClientHelloSpec
4. Stored profile
5. Selected preset name
```

Outbound JA3, JA4 и TLS-NORM MUST вычисляться из фактически записанных байтов.
Preset и spec выражают намерение, но не доказывают результат.

## 7. Привязка к релизам

### MVP-0

К существующим критериям добавляются архитектурные инварианты:

- `ARCH-UTLS-001`, `ARCH-UTLS-002`, `PR-UTLS-001`;
- `SEC-WIRE-001` для каждого outbound handshake;
- engine/parser/fingerprint version metadata в observation;
- unknown numeric IDs не вызывают parse failure;
- uTLS dependency закреплена точной версией.

MVP-0 не обязан публиковать Profile Compiler UI или Replay Lab.

### MVP-2

Дополнительно обязательны:

- Profile Compiler и `ClientHelloSpec` runtime model;
- PRESET, OBSERVED, CUSTOM, RANDOMIZED;
- STRICT/ADAPTIVE и явные ALPN/ALPS policies;
- selected/compiled/actual separation;
- трёхуровневая verification;
- engine compatibility status и mutation audit;
- support level для extensions;
- local round-trip validation перед публикацией observed profile.

### Release 5

Обязательны Replay Lab, Compatibility Matrix, controlled Roller, расширенная
fidelity matrix, pre-marshaled diagnostics, reparse workflow и связанные
варианты full/resumed/PSK fingerprints.

Требования безопасности, wire capture и versioning применяются с первого
релиза, в котором появляется соответствующая функция, и не откладываются до
Release 5.

## 8. Дополнительные критерии приёмки

1. CI подтверждает, что `go.mod` содержит точную версию uTLS, не branch/latest.
2. Golden report сравнивает actual wire до и после обновления uTLS.
3. Observed Profile создаётся через reassembled raw → `utls.Fingerprinter`.
4. STRICT profile не изменяет ALPN/ALPS молча и возвращает
   `PROFILE_PROTOCOL_CONFLICT` при несовместимости.
5. ADAPTIVE profile сохраняет каждую runtime mutation с before/after/reason.
6. RANDOMIZED observation содержит фактические JA3/JA4/TLS-NORM.
7. Engine mismatch даёт `PROFILE_REVALIDATION_REQUIRED`, пока local replay не
   завершится статусом VALID или VALID_WITH_DIFFERENCES.
8. Unknown extension сохраняет ID, position, raw bytes и support level.
9. Profile→spec, spec→wire и inbound→outbound diff доступны отдельно.
10. Production routing не использует Roller.

## 9. Правило сопровождения

Изменения реализации выполняются относительно этого ТЗ v3. Документы
состояния реализации обязаны различать `реализовано`, `частично`,
`не реализовано` и не могут объявлять весь релиз готовым без всех его
артефактов приёмки. Любое обновление uTLS сначала изменяет compatibility
baseline и golden report, затем код и только после этого production pin.

## 10. Дополнение: единый приоритетный backlog реализации

Этот backlog сводит в один упорядоченный список известные незакрытые задачи
проекта и дополняет критерии релизов выше. Он не отменяет требования разделов
1–9, не снижает критерии MVP и не разрешает объявлять релиз готовым при
невыполненных обязательных критериях. Задачи выполняются сверху вниз; следующая
может начаться раньше только если предыдущая объективно заблокирована внешним
условием. В таком случае блокер и доказательство проверки фиксируются в
`RECORDER_IMPLEMENTATION.md`, после чего работа продолжается со следующей
задачей.

### P0 — воспроизводимость и корректность основы

1. **Восстановить и закрепить полный Go quality gate.** Обеспечить доступный
   поддерживаемый Go toolchain и форматтер; прогнать `gofmt`,
   `go build ./...`, `go test ./...`, `go vet ./...` и `go test -race ./...`.
   Исправить найденные регрессии. Готово, когда все команды успешно выполнены
   на чистом checkout и их результаты воспроизводимы в CI.
2. **Перевести постоянное состояние приложения на SQLite.** Использовать одну
   SQLite-базу для наблюдений и управляемых сущностей (в частности, TLS-профилей,
   устройств/приложений/назначений, правил маршрутизации и upstream TLS
   профилей). Ввести версионируемые транзакционные миграции и безопасный импорт
   существующих JSON/JSONL данных без потери истории. JSON допускается для
   импорта/экспорта, но не как основной постоянный store. Готово, когда все
   runtime CRUD переживает перезапуск, миграции идемпотентны, а тесты проверяют
   импорт, rollback при ошибке и целостность БД.
3. **Закрыть корректность захвата TLS ClientHello.** Проверить fragmented
   records/handshakes, границы размеров и повторный ClientHello после
   HelloRetryRequest для каждого поддерживаемого режима перехвата. Для
   неподдерживаемого случая возвращать точный статус/причину, а не выдавать
   неполный результат за полный. Готово, когда parser и интеграционные тесты
   подтверждают reassembly и соответствие результата исходным байтам.
4. **Доказать соответствие fingerprint фактическому outbound wire.** Для JA3,
   JA4 и TLS-NORM обеспечить тестовый путь от реально записанного исходящего
   ClientHello, отдельно от preset/spec. Готово, когда golden-тесты сравнивают
   фактические wire bytes, повторный parse и вычисленные fingerprint, включая
   различие выбранного и реально отправленного профиля.
5. **Завершить режимы STRICT и ADAPTIVE.** STRICT должен отклонять
   несовместимую конфигурацию без молчаливой мутации; ADAPTIVE — фиксировать
   каждую мутацию с исходным/итоговым значением и причиной. Готово, когда
   контракт API, UI, аудит и тесты покрывают конфликт ALPN/ALPS, extensions и
   ограничения TLS engine.

### P1 — завершение TLS-профилей и приёмочных доказательств

6. **Завершить lifecycle возобновлённых TLS-сессий.** Проверить полный
   handshake, TLS 1.3 PSK/resumption и повторные подключения с реальным
   session cache; сохранять фактически наблюдённые варианты ClientHello и
   различать FULL/RESUMED/PSK. Готово, когда integration-тест подтверждает
   повторное использование сессии и корректность каждого fingerprint.
7. **Связать варианты отпечатков в Fingerprint Family.** Реализовать модель
   семейства и явные/автоматические связи между вариантами профиля, включая
   initial/resumed TLS и соответствующие HTTP fingerprint. Готово, когда
   группировка доступна в API/UI и не объединяет несовместимые варианты без
   объяснимого основания.
8. **Добавить регрессионный gate для обновления uTLS.** Закрепить baseline
   профилей, outbound wire и golden reports; обновление версии должно выявлять
   изменения до production pin. Готово, когда CI блокирует непроверенное
   изменение baseline и публикует понятный diff.
9. **Закрыть обязательные приёмочные доказательства MVP.** Получить локальные
   реальные Safari/iOS и Android/OkHttp captures и записать для проверки
   устройство, версию ОС/приложения и способ захвата; raw captures хранить
   локально и не добавлять в Git. Провести нагрузочное измерение собранного
   бинарного файла с recorder on/off и сообщить p95/throughput. Публикация или
   распространение captures не требуются. Готово по критериям
   `MVP0_ACCEPTANCE.md`.
10. **Завершить управление пользователями и токенами.** Реализовать заявленные
    роли, создание/отзыв/ротацию токенов и их действие без перезапуска.
    Локальный режим по принятому требованию пользователя не должен требовать
    авторизацию или HTTPS; это исключение ограничено локальным режимом и должно
    быть ясно отражено в документации. Готово, когда API, UI, аудит и тесты
    подтверждают весь lifecycle и разграничение режимов.
11. **Завершить HTTP/1 fingerprint coverage.** Поддержать и проверить
    chunked body, trailers и close-delimited response, либо явно обозначить
    каждое ограничение и не считать fingerprint полным. Готово по протокольным
    тестам на границы и фрагментацию.
12. **Завершить HTTP/2 fingerprint coverage.** Расширить разбор нужных frame,
    SETTINGS и HPACK-полей в пределах зафиксированного контракта; недоступные
    значения должны маркироваться, а не подменяться предположениями. Готово,
    когда документирована матрица покрытия и она проверяется golden-векторами.

### P2 — дополнительные сенсоры и расширение наблюдений

13. **Добавить passive TCP sensor и JA4T** с определёнными точками захвата,
    поддержкой IPv4/IPv6 и тестами, не влияющими на proxy forwarding.
14. **Добавить DNS sensor и корреляцию DNS→TLS** для UDP/TCP запросов и
    ответов. Корреляция должна быть ограничена временем/идентификаторами потока,
    явно сообщать неоднозначность и иметь тесты переупорядочивания/потери.
15. **Добавить QUIC v1/v2 Initial sensor.** Реализовать разбор Initial,
    derivation Initial keys, сборку CRYPTO frames и извлечение ClientHello /
    transport parameters; неподдерживаемые варианты не должны отображаться как
    успешно распознанные.
16. **Обогатить разбор серверной стороны TLS.** EncryptedExtensions
    анализировать только при наличии разрешённых session secrets; иначе
    сохранять корректный статус «зашифровано/недоступно» и причину. Не обещать
    расшифровку из одного пассивного захвата.
17. **Автоматизировать обнаружение и привязку версии приложения.** Разделить
   наблюдаемые признаки, ручное подтверждение и вывод версии; указывать
   источник и уверенность, не выдавая эвристику за достоверный факт. HTTP
   User-Agent может давать только ограниченные product/version claims со
   статусом `unverified` и низкой уверенностью; исходное значение не хранить.
   Такие claims не связывать с приложением/устройством и не использовать в
   policy до явного подтверждения через time-bounded device assignment. Поля
   `application_version` должны отражать подтверждённую привязку, а не claim.

### P3 — полнота продукта и косметика

18. **Завершить UI/API для наблюдений и истории.** Обеспечить поиск,
    фильтры, карточку деталей, сравнение и повторный разбор для реализованных
    типов fingerprint; API и OpenAPI должны совпадать с фактическим поведением.
19. **Завершить централизованное управление секретами и ротацией.** Определить
    единый provider для секретов, сроков действия и ротации ключей/локальных
    CA; не хранить секреты в экспортируемых профилях или журналах.
20. **Выполнить финальную редакционную и визуальную полировку.** Устранить
    устаревшие даты/ссылки, унифицировать русские термины, проверить навигацию,
    доступность и согласованность экранов. Этот пункт выполняется после
    функциональных и приёмочных пунктов.

### Правило статуса backlog

Наличие пункта в этом списке само по себе не означает, что он не реализован:
перед началом каждого пункта сверить код, тесты и актуальный
`RECORDER_IMPLEMENTATION.md`, затем отметить его как `реализовано`, `частично`
или `не реализовано` с перечислением подтверждающих тестов. Статус
`реализовано` допустим только после прохождения критериев готовности пункта;
невыполненные внешние приёмочные доказательства не закрываются наличием
синтетических тестов.
